# Technical writing

Prefer concrete explanation over polished abstraction.

- Describe behavior before benefits.
- State the mechanism, observable behavior, or measured result instead of how a
  feature feels.
- Replace abstract role or process language with the actor and concrete action.
  Include the constraint or result when the source supports it.
- Name the source behind attributed claims, or remove the attribution. Never
  invent supporting evidence.
- Prefer a plain word unless a domain term is more exact.
- Use consistent terminology. Repeat a term when that is clearer than cycling
  through synonyms.
- Remove unsupported adjectives and hedges that do not change the claim.
- Let the content determine the structure. Do not force a contrast, reversal,
  range, or list length.
- Remove an inline label or lead-in when it merely restates the sentence it
  introduces. Preserve structural headings and labels that add context.
- Preserve functional UI labels, standard headings, exact technical terms, and
  useful domain or search terms. Terse does not mean generic when it has a job.
- Split unrelated or dense claims.
- Keep necessary terms, qualifications, causes, and consequences.
- Skip generic introductions and conclusions.
- On the final pass, apply both semantic tests:
  - Portability: could this fit unchanged in an unrelated project or
    professional post? Make it specific or cut it.
  - Spoken language: would a domain expert say this while explaining the work to
    a coworker? Rewrite it unless the format requires formal language.
